# 测试

测试按验证边界分为单元测试、进程内集成测试和进程端到端测试。

| 层级 | 入口 | 验证范围 |
| --- | --- | --- |
| 单元测试 | `cargo test-unit` | 解析、协议转换、状态迁移、渲染和单组件行为 |
| 集成测试 | `cargo test-integration` | 会话、工具、权限、日志、恢复和传输之间的协作 |
| 进程端到端测试 | `cargo test-e2e` | 真实 CLI 的参数、配置、工具执行、输出、退出和重启恢复 |

`cargo test --locked` 运行全部默认测试。格式与静态检查使用以下命令。

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
```

## 组织

进程内测试留在原 crate，保留私有实现的测试访问。集成测试的完整名称包含 `integration_tests::`。两个进程内入口使用 libtest 名称过滤，运行集合互斥，编译过程不隔离。

进程端到端测试位于 `tests/cli.rs`。Cargo 将这个文件编译为 integration test target；这里按进程边界称为端到端测试。

局部测试不会仅因使用 Tokio、其他模块的类型或临时文件而归入集成层。分类依据是它实际验证的协作边界。

## 确定性与隔离

时间逻辑优先使用显式时间输入或 Tokio 虚拟时间。真实 TCP 和进程测试使用信号协调执行，用有界超时防止挂起。OS 文件锁与重试测试保留真实时钟，不受 Tokio 虚拟时间控制。

端到端测试使用临时 HOME、配置、工作目录和本地模型服务。模型响应由测试控制，工具执行、日志和恢复使用生产实现，不调用付费 provider，也不读取用户配置。

真实 provider、终端进入与恢复、剪贴板和终端显示效果属于环境验证。上述自动化测试不代表这些环境行为已经验证。

## 保留标准

每个测试应保护当前契约，并能指出一种会使断言失败的错误行为。预期结果应独立于被测计算，避免将同一数据源的不同访问器相互比较。

相同规则的样例可以合并，但保留有区别的输入边界和失败诊断。删除重复覆盖前，确认保留的测试保护同一契约。测试数量和覆盖率不作为单独的通过标准。
