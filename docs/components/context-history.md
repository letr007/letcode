# 历史整理与证据恢复

letcode 引入内部专家 `historian` 增量整理会话历史。系统采用三档表述，并基于自身的日志记录、运行时投影与协议适配器实现。

## 三档表述机制

Historian 每次读取尚未整理的前缀片段。读取上限为该路由可用输入预算的四分之一（在 2 万至 5 万 Token 之间），剩余预算保留给后续请求。系统按任务目标将历史切分为段落，每段一次性生成三种表述：

- **详细档（Detailed）**：记录目标、重要步骤、失败原因、关键纠错与排查定位；
- **紧凑档（Compact）**：记录最终结论、核心决策、当前约束与关键索引；
- **线索档（Anchor）**：记录执行结果与检索关键词；若标题足以表明上下文，正文可留空。

表述档位的选择是确定性的，系统不会为了调整档位重复调用模型。当上下文预算缩小时，系统选用更简短的档位或进行归档；归档仅调整在活跃上下文中的展示形态，不删除原始日志文件。当预算恢复充裕时，系统可重新切回详细档位。

三档是同一历史段落的三种不同表述。系统不按“摘要、证据、原文”分层存储。模型提炼可能遗漏细节，必要时应回查原始记录，不把提炼内容视作绝对事实。

## 准备、发布与应用

`HistoryPublished` 保存经过来源校验的历史段落，同时兼容读取旧日志中的事实字段。`HistoryApplied` 确定进入当前上下文的历史段落与档位，并标记对应原始消息已被覆盖。发布操作不会删除原始消息。应用后系统追加一条内部续接消息，重申未完成的待办事项与自动继续状态。这些状态保存在运行时快照中，未写入普通文本，仅靠历史总结容易丢失。

活跃历史划分为稳定基线、增量更新区和最近的原始对话尾部。普通请求直接复用已选定的表述，增量整理优先保持基线稳定。遇到输入预算吃紧、手动触发压缩或增量堆积过多时，系统重新生成基线。重新生成基线反映上下文重排，不代表服务商缓存必然失效。

后台整理任务绑定特定的会话、分支和检出版本。任务运行期间，主会话可以继续接收并写入用户消息；新历史应用在最新投影之上，避免旧状态覆盖新内容。取消操作与发布流程共享原子提交边界：已提交的产物完整保留，发布前取消则不会产生额外写入。

手动执行 `/compact` 同样复用该三档机制。旧版本会话检查点可完整读取并作为旧基线保留；系统不会自动花费 Token 重建旧历史，也不会在整理失败时回退为粗暴的全文滚动截断。

## Historian 专家路由

未指定配置时，Historian 默认使用主模型路由。用户也可以为其配置独立路由：

```toml
[agents.historian]
provider = "your-provider"
model = "your-model"
```

指定模型必须已在服务商配置中定义。Historian 不强制要求模型支持结构化输出；数据格式由专用提示词与宿主解析器共同保障。模型响应按行读取，每行对应一个历史段落。若首行解析失败或分段游标停滞，系统丢弃异常部分，发布已成功解析的前缀，剩余内容留待后续任务处理。若返回格式损坏，系统会使用纠错提示重新发起一次修复调用。

Historian 采用纯文本单次执行请求，静态系统指令放入原生高权威字段，不占用工具循环，禁止递归委派。处理范围在发送前按预算和分片上限进行校验。若同一前缀连续整理失败达到阈值，系统启动冷却退避，期间暂停重发，冷却结束后再行尝试。

后台请求会产生相应的 Token 用量。子视图实时展示服务商返回的用量与缓存数据；未报告时明确标识，不填充推测数据。增量事件可能代表累计用量，不能简单相加。

## 审计证据与项目记忆

工具返回的观察结果、子代理汇报与引用来源均写入会话内的证据记录 `EvidenceRecord`。证据用于当前会话的内容筛选与行为审计，不充当跨会话知识库。旧日志中已记录的事实继续按原样解析展示，磁盘 JSONL 文件不执行批量迁移或重写。

跨会话的项目记忆由独立后台任务在交互回合完全持久化后增量提取。它复用 Historian 的单次执行路由，但使用独立的提取提示词。记忆按工作区路径严格隔离，存储在配置目录下的本地 SQLite 数据库中。首次启用仅记录当前日志游标，不全盘扫描或回溯旧会话。会话的撤销、分支切换或文件删除不影响已经入库的项目记忆。若同一游标位置连续提取失败，系统按 1 分钟、5 分钟、30 分钟、2 小时至 6 小时递增退避重试，连续失败 8 次后停止自动重试；新回合产生后重置计数。

普通请求不会自动载入全量项目记忆。模型仅在任务需要时调用 `memory__recall`，根据关键词、文件路径、类型和状态进行检索。检索结果保留来源会话、分支与记录 ID，便于回查原始上下文。项目记忆可能存在滞后，仅供辅助参考，不能替代最新代码事实、用户明确要求和权威配置。

记忆库状态明确区分缺失、同步中、失败、空白与就绪五种情况。检索失败时直接反馈状态，不会静默重放历史会话。

## 历史检索与原文展开

系统提供以下只读查询工具：

- `context__search`：检索原始对话、已归档历史段和证据记录，返回有限长度的文本预览与来源 ID；
- `context__expand`：根据 ID 读取历史段对应的完整原始消息或工具输出摘录；
- `memory__recall`：按关键词、路径、类别与状态检索当前工作区的独立项目记忆库。

这些工具默认作用于当前会话、当前分支与当前上下文节点。指定跨会话或跨分支查询时，结果会显式标明所属来源。展开操作严格只读，不会恢复旧的运行时状态，也不会重新执行历史工具。证据详情属于正文摘录，不代表完整的原始输出。

内置工具生成的大体积输出在存入会话日志前，其完整正文会单独转存到会话目录下的 `artifacts/<session-id>/` 中。系统使用内容散列寻址，持久化成功后将文件路径填入工具返回值。模型可以通过 `fs__read` 或 `search__rg` 查看完整大文件。若本地临时文件丢失，系统无法从摘要反向恢复原文。

## TUI 界面呈现

后台整理任务在 TUI 底部状态栏以图标静默呈现，不向主时间线插入多余的工具卡片，也不改变主任务的忙碌指示。遇到异常时，图标会变化并提示用户查看详情。

用户可以通过已有的子会话导航面板，调出 Historian 的结构化报告。界面展示任务概览、分段正文、使用模型、耗时和 Token 消耗。在 Historian 子视图且输入框为空时：

- 按键 `1`：查看精简版摘要；
- 按键 `2`：查看详细版内容；
- 按键 `3`：查看线索与检索项；
- 按键 `0`：查看完整的原始 JSON 报告；
- 按键 `s`：切换是否展示完整的来源 ID。

切换查看方式仅影响当前界面渲染，不改变主模型采用的历史档位。来源 ID 专供复制使用，不支持直接点击跳转。项目记忆的后台提取任务同样不会在时间线插入干扰卡片。

界面标注“产物已生成”仅代表后台计算完毕，不代表主会话已经完成发布或应用。Token 用量与缓存数据展示服务商最近一次的更新值；缺失时明确显示“未报告”。旧版 Markdown 格式的报告保持原样输出。内部整理报告不作为普通决策证据重新输入给主模型。

手动执行 `/compact` 或主流程等待整理时，底部状态栏会显示扫描动画与提示文本。操作完成后给出提示，不展示缺乏依据的百分比进度条。整理过程不会在主时间线产生多余的空行或占位块。

- `src/agent/history_runtime.rs`：负责前缀准备、请求边界应用与预算控制。
- `src/session/historian.rs`：管理内部专家任务派发、取消处理与产物发布。
- `src/transcript/transcript_projection/`：处理分支状态恢复、来源校验与活跃上下文投影。
- `src/evidence.rs`：收集会话内观察证据、溯源信息与旧事实格式转换。
- `src/project_memory/`：实现基于 SQLite 的工作区隔离记忆库与后台提取服务。
- `src/memory.rs`、`src/tool/memory.rs`：定义项目记忆数据结构与只读检索工具。
- `src/tool/context_history.rs`、`src/tool/fold_artifact.rs`：提供历史原文检索工具与大文本折叠保存逻辑。
