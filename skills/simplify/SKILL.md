# 代码简化

## 目标

在完整保留行为的前提下降低代码复杂度。目标不是减少行数，而是让代码更容易阅读、理解、修改和调试。每次简化都应让新加入项目的成员更快看懂代码。

## 适用场景

- 功能已经正常工作且测试通过，但实现比实际需要更复杂
- 代码审查发现可读性或复杂度问题
- 代码存在深层嵌套、函数过长、命名不清、重复或风格不一致
- 已经理解在时间压力下编写的代码，准备改善其结构

代码已经足够清晰、行为尚未理解、简化会破坏已确认的性能要求，或相关代码即将被替换时，不要使用此 Skill。

## 原则

### 完整保留行为

不要改变输入、输出、副作用、执行顺序、错误行为或边界情况。无法确认等价时，不要修改。

每次修改前检查：

- 所有输入是否仍会得到相同结果？
- 错误行为和副作用是否保持不变？
- 重要的执行顺序是否未被改变？
- 现有测试是否无需削弱就能通过？

### 遵循项目约定

先阅读仓库指令和相邻代码。遵循项目已有的命名、导入、控制流、错误处理和类型风格，不要强加外部偏好。

### 清晰优先

当紧凑写法需要额外思考才能理解时，应选择更明确的代码结构。可以展开密集的控制流，但要保留承载业务含义的名称和中间变量。

### 保持适度

不要内联有意义的概念，不要合并无关职责，不要移除有助于测试的抽象，也不要以减少行数为目标。

### 限定改动范围

默认只处理近期修改或用户明确指定的代码，避免顺手重构无关部分。

## 流程

### 1. 理解后再修改

先确认代码职责、调用方、依赖、边界情况、测试，以及当前写法存在的原因。任何一项不清楚时，应继续阅读上下文。

### 2. 找到具体问题

重点检查深层嵌套、职责混杂、重复条件、误导性命名、重复逻辑、死代码，以及没有实际价值的包装层或抽象。

### 3. 渐进修改

每次只做一项完整、连贯的简化，随后运行相关检查。只有行为仍得到验证时，才保留该修改。

### 4. 验证结果

确认修改后的代码更容易理解、仍符合项目约定、差异范围集中，并且行为和错误处理没有变化。

## 验证清单

- [ ] 现有测试无需修改即可通过
- [ ] 相关构建、类型检查、静态检查和格式化检查通过
- [ ] 未重构无关文件
- [ ] 错误处理和副作用保持不变
- [ ] 修改后的代码比原实现更容易审查
