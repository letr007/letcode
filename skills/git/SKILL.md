# Git 工作流

任务涉及仓库状态、差异、提交、分支、远程仓库、GitHub Pull Request 或发布相关 Git 检查时，使用此 Skill。

如果只是讨论 Git 概念，且用户没有要求操作具体仓库，则无需使用。

## 通用规则

- 以仓库的真实状态为准。
- 除非用户要求实现功能或操作仓库，否则不要修改文件。
- 只有用户明确要求时才能提交。
- 未经明确要求，不要推送、强制推送、修订提交、跳过钩子、创建空提交、删除分支或更改远程仓库。
- 不要提交密钥、凭据、本地环境文件、构建产物或无关变更。
- 只暂存预期文件。除非已经检查并确认所有变更都应提交，否则不要使用 `git add .`。
- 仓库状态与预期不符时，应停止操作并说明阻塞原因，不要掩盖问题。

## 检查仓库变更

用户要求检查或总结变更时：

1. 使用 `git status --short --branch` 检查分支与工作区状态。
2. 使用 `git diff` 检查相关差异；存在已暂存变更时，再检查 `git diff --cached`。
3. 总结变更文件、改动意图、风险和建议的后续操作。
4. 除非用户另有要求，否则不要暂存、提交或修改文件。

## 提交变更

用户明确要求提交时：

1. 检查 `git status --short --branch`。
2. 使用 `git diff` 检查未暂存变更。
3. 存在已暂存变更时，使用 `git diff --cached` 检查。
4. 使用 `git log --oneline -10` 查看近期提交风格。
5. 根据用户需求和实际差异确定提交范围。
6. 只暂存预期文件。
7. 提交前再次检查已暂存差异。
8. 使用符合仓库风格的简洁提交信息；仓库采用约定式提交时，应遵循该格式。
9. 让钩子正常运行。钩子失败时，检查原因并只修复相关问题；除非用户明确要求，否则不要跳过钩子。
10. 返回提交哈希和简要说明。

## 创建 GitHub Pull Request

用户要求创建 PR 时：

1. 检查 `git status --short --branch`。
2. 检查当前分支、上游分支和近期提交。
3. 根据用户要求或仓库惯例确定目标基础分支。
4. 检查相对基础分支的差异，并审查 PR 包含的全部提交。
5. 创建 PR 前，确认工作区状态符合预期。
6. 可以使用时，优先通过 `gh` 执行 GitHub 操作。
7. 创建成功后返回 PR URL。

只有用户明确要求创建 PR 或推送，并且已经检查仓库状态时，才能推送或发布分支。

## 发布相关检查

准备发布时：

- 检查当前分支以及工作区是否干净。
- 按需检查近期提交和标签。
- 除非用户明确要求，否则不要创建标签、推送标签或发布版本。
- 生成变更日志或发布说明时，只涵盖用户要求的版本范围。

## 输出格式

Git 操作报告应保持简洁，包含：

- 当前分支和状态
- 涉及的文件或提交
- 已执行的操作
- 剩余风险或阻塞项
